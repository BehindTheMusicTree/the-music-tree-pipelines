# AGENTS.md — pipelines/wikidata

Supplements the root `AGENTS.md` when working inside this pipeline. See the root file for repo-wide setup, conventions, and the `musicbrainz` pipeline.

## Commands

- **Bronze:** `uv run --package wikidata python -m wikidata.ingest` (after geohistory Bronze: reads `GEOHISTORY_BRONZE_DIR/natural_earth_admin.parquet`)
- **Silver:** `uv run --package wikidata python -m wikidata.silver` (reads `BRONZE_OUTPUT_DIR/wikidata_genre_tree.parquet`, runs all nine steps in sequence, writes `SILVER_OUTPUT_DIR/1_item_links.parquet`, `2_non_genre_pruning.parquet`, `3_regional_overview_classification.parquet`, `4_regional_classification.parquet`, `5_parent_selection.parquet`, `5_secondary_parents.parquet`, `6_canonical_parents.parquet`, `7_canonical_hierarchy.parquet`, `8_regional_hierarchy.parquet`, and `9_canonical_roots.parquet`)

## Architecture

**Bronze:** queries the public Wikidata SPARQL endpoint (`https://query.wikidata.org/sparql`) live — no local DB. Pulls every item classified `P31` "instance of" music genre (`Q188451`) plus each genre's direct `P279` "subclass of" parent edges (unfiltered — pruning to genre-only parents is Silver-layer work), writes `wikidata_genre_tree.parquet`. A further step, `ingest_descriptions`, writes `wikidata_genre_descriptions.parquet` for every tree QID (children and parents of `wikidata_genre_tree.parquet`, plus the curated `regional_overview_additions.csv` from `CURATION_BRONZE_DIR`): English description and enwiki article from `wbgetentities` (whose English aliases also go to `wikidata_genre_aliases.parquet`), intro from the Wikipedia extracts API in `src/wikidata/wikipedia_client.py`; it runs after the tree step and only `gold` reads it. Two more steps, `ingest_cultural_entities` and `ingest_cultural_entity_claims`, write `wikidata_cultural_entity.parquet` (items with a Glottocode, archaeological cultures, civilizations, historical and modern countries, cultural regions, notable historical regions and ethnic groups, macro regions) and `wikidata_cultural_entity_claim.parquet` (dates kept as raw literals with precision, plus succession/part-of/coordinates) for `geohistory`; they run last and no Silver step reads them yet. So do `ingest_admin_hierarchy`, writing `wikidata_admin_hierarchy.parquet` (the `P131`/`P361` ancestry of the Natural Earth admin units read from `GEOHISTORY_BRONZE_DIR`, so geohistory Bronze must run first), and `ingest_cultural_entity_aliases`, writing `wikidata_cultural_entity_alias.parquet`. See `src/wikidata/wikidata_client.py`.

**Silver (`src/wikidata/silver/`):** a preliminary `curation_resolution` step rewrites merged/deleted QIDs in the Bronze curation CSVs in place (live `wbgetentities` call, only when a curated QID is unknown) and writes `curation_resolutions.json`; then nine sequential steps, each reading the previous step's output. `1_item_links` derives a browsable Wikidata page URL (`item_url`/`parent_url`) from each row's `item_id`/`parent_id`, and adds `has_item_label`/`has_parent_label` flags, `False` where the label service fell back to printing the QID (no label in any queried language). `2_non_genre_pruning` drops theme/technique/out-of-scope/non-stylistic items entirely, via four curated manual CSV backstops (`theme_genres.csv`, `technique_genres.csv`, `out_of_scope_genres.csv`, `umbrella_non_stylistic_genres.csv`) — this isn't about region, it's non-genre pruning that runs as early as possible, before regional classification (or any other downstream step) sees the tree. `3_regional_overview_classification` flags (not drops) rows whose `item_label` is a Wikidata "music of \<place\>" regional-overview article (e.g. "music of Kenya") rather than an actual genre — it also reads a curated `regional_overview_additions.csv` as a backstop for real overview items entirely absent from Bronze (not even as a `parent_label`). `4_regional_classification` cascades the regional-overview seed set down through parent edges to flag every nationally/ethnically-specific genre (e.g. "fado", "morna") as regional, as opposed to canonical genres like "rock music" — it also reads a curated `canonical_parent_additions.csv` (columns `item_id,item_label,reason`) for synthetic `LOCAL:`-prefixed canonical grouping nodes with no real Wikidata QID (e.g. `LOCAL:reggae-dub`, "Reggae/Dub"), and three curated parent lists, one per parent axis, each row applied as a synthetic edge ahead of step 5: `canonical_parent.csv` (`relation_type` `manual_canonical_parent`, parent must stay canonical), `regional_genre_parent.csv` (`manual_regional_genre_parent`, parent must be regional) and `regional_overviews.csv` (`manual_regional_overview`, keyed by `item_id` + `overview_item_id`, also seeds `regional_reason = "manual_regional_overview"` for the rare genre none of the automated seed/`indigenous_to`/`country_of_origin` sources catch); each has an optional `exclude_other_parents` column dropping the item's other candidates of the same axis. `forced_canonical_genres.csv` lists genres kept canonical despite a regional edge (e.g. Baroque music): never flagged regional, the cascade stops at them. `5_parent_selection` splits each item's parents into three axes — 0 or 1 canonical parent, 0 or 1 regional genre parent (the other candidates of both going to a sibling `5_secondary_parents.parquet`), 0 to n regional overviews (minus any overview that is an ancestor of another kept parent) — a curated edge winning its axis, else a provisional lowest-QID heuristic; it writes `canonical_parent_id`, `regional_genre_parent_id`, `regional_overview_ids` and the item's anchor `parent_id` (regional genre parent, else first overview, for a regional item; canonical parent otherwise) to `5_parent_selection.parquet`. `6_canonical_parents` flags (`canonical_parent_is_genre`) whether each row's anchor parent is itself a real genre. `7_canonical_hierarchy` is the first step that prunes rather than flags: it collapses the edge list to one row per non-regional genre item, producing `7_canonical_hierarchy.parquet` (canonical, excludes regional items) with an `is_umbrella` flag from the curated `umbrella_stylistic_genres.csv` (a genre kept in the tree but never assigned songs directly, e.g. techno; an unknown, regional or leaf id raises). `8_regional_hierarchy` mirrors that pruning restricted to regional items, producing `8_regional_hierarchy.parquet`. `9_canonical_roots` extracts `7_canonical_hierarchy`'s root items (no parent) into their own `9_canonical_roots.parquet`, for manual exploration of the "too many roots" open question below — it also reads a curated `accepted_canonical_roots.csv` (whose items `4_regional_classification` pins as parentless roots, so Wikidata re-parenting or `indigenous_to` can't move them; an accepted id that's absent or curated regional raises) and flags (`is_accepted = false`, logged as a WARNING) any root not already in it, rather than failing the run; Gold carries the flag into the canonical tree export as `isUnacceptedRoot: true` so grow-the-music-tree-api queues it for admin review. Artist images run independently through `python -m wikidata.artist_images`; Gold consumes immutable publications rather than numbered Silver image outputs. See `DESIGN.md` for the rationale and rules behind each step (e.g. the regional cascade's seed set, the parent-selection heuristic — several explicitly marked provisional/exploration-phase there) and `SCHEMA.md#3-silver` for the full column definitions and profiling detail. `7_canonical_hierarchy` (canonical) currently surfaces a high number of root items; whether that reflects the source data or an upstream pruning artifact is an open exploration — see `notebooks/explore_genre_tree.ipynb`.

**Curation input:** every curation CSV this pipeline reads comes from `CURATION_BRONZE_DIR` — the `curation` pipeline's Bronze output, pulled from `grow-the-music-tree-api` (the source of truth, edited via its `curation/<list>/entries/` endpoints or the grow admin UI). Run `uv run --package curation python -m curation.ingest` first. Bronze also reads `entity_additions.csv` for the cultural entities (kind `curated`) and `tradition_additions.csv` for the music-tradition candidates.

**Target shape (design intent, not yet reached):** the canonical tree (`7_canonical_hierarchy`) should collapse down to a handful of root genre families — rock, blues, jazz, funk/disco, electronic, hip-hop, reggae/dub, classical music, etc. — not the hundreds of roots it currently produces. Getting there is expected to be mostly a linking/cleaning problem (correcting mis-selected canonical parents, e.g. the lowest-QID fallback in `5_parent_selection`), not a new extraction or classification mechanism. The regional tree (`8_regional_hierarchy`) follows different logic entirely: one root per cultural/geographic region (e.g. "music of Cape Verde"), with each region's own genres nested underneath — it is not expected to collapse to a small root count the way the canonical tree is.
