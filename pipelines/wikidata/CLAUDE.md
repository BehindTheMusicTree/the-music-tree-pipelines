# CLAUDE.md — pipelines/wikidata

Supplements the root `CLAUDE.md` when working inside this pipeline. See the root file for repo-wide setup, conventions, and the `musicbrainz` pipeline.

## Commands

- **Bronze:** `uv run --package wikidata python -m wikidata.ingest` (after geohistory Bronze: reads `GEOHISTORY_BRONZE_DIR/natural_earth_admin.parquet`)
- **Silver:** `uv run --package wikidata python -m wikidata.silver` (reads `BRONZE_OUTPUT_DIR/wikidata_genre_tree.parquet`, runs all nine steps in sequence, writes `SILVER_OUTPUT_DIR/1_item_links.parquet`, `2_non_genre_pruning.parquet`, `3_regional_overview_classification.parquet`, `4_regional_classification.parquet`, `5_main_parent_selection.parquet`, `5_secondary_parents.parquet`, `6_canonical_parents.parquet`, `7_canonical_hierarchy.parquet`, `8_regional_hierarchy.parquet`, and `9_canonical_roots.parquet`; then the artist image steps write `10_commons_image_metadata.parquet` and `11_artist_images.parquet`, which need `COMMONS_METADATA_MAX_BATCHES_PER_RUN`)

## Architecture

**Bronze:** queries the public Wikidata SPARQL endpoint (`https://query.wikidata.org/sparql`) live — no local DB. Pulls every item classified `P31` "instance of" music genre (`Q188451`) plus each genre's direct `P279` "subclass of" parent edges (unfiltered — pruning to genre-only parents is Silver-layer work), writes `wikidata_genre_tree.parquet`. A further step, `ingest_descriptions`, writes `wikidata_genre_descriptions.parquet` for every tree QID (children and parents of `wikidata_genre_tree.parquet`, plus the curated `manual_regional_overview_additions.csv` from `CURATION_BRONZE_DIR`): English description and enwiki article from `wbgetentities` (whose English aliases also go to `wikidata_genre_aliases.parquet`), intro from the Wikipedia extracts API in `src/wikidata/wikipedia_client.py`; it runs after the tree step and only `gold` reads it. Two more steps, `ingest_cultural_entities` and `ingest_cultural_entity_claims`, write `wikidata_cultural_entity.parquet` (items with a Glottocode, archaeological cultures, civilizations, historical and modern countries, cultural regions, notable historical regions and ethnic groups, macro regions) and `wikidata_cultural_entity_claim.parquet` (dates kept as raw literals with precision, plus succession/part-of/coordinates) for `geohistory`; they run last and no Silver step reads them yet. So do `ingest_admin_hierarchy`, writing `wikidata_admin_hierarchy.parquet` (the `P131`/`P361` ancestry of the Natural Earth admin units read from `GEOHISTORY_BRONZE_DIR`, so geohistory Bronze must run first), and `ingest_cultural_entity_aliases`, writing `wikidata_cultural_entity_alias.parquet`. See `src/wikidata/wikidata_client.py`.

**Silver (`src/wikidata/silver/`):** a preliminary `curation_resolution` step rewrites merged/deleted QIDs in the Bronze curation CSVs in place (live `wbgetentities` call, only when a curated QID is unknown) and writes `curation_resolutions.json`; then nine sequential steps, each reading the previous step's output. `1_item_links` derives a browsable Wikidata page URL (`item_url`/`parent_url`) from each row's `item_id`/`parent_id`, and adds `has_item_label`/`has_parent_label` flags, `False` where the label service fell back to printing the QID (no label in any queried language). `2_non_genre_pruning` drops theme/technique/out-of-scope/non-stylistic items entirely, via four curated manual CSV backstops (`manual_theme_genres.csv`, `manual_technique_genres.csv`, `manual_out_of_scope_genres.csv`, `manual_non_stylistic_genres.csv`) — this isn't about region, it's non-genre pruning that runs as early as possible, before regional classification (or any other downstream step) sees the tree. `3_regional_overview_classification` flags (not drops) rows whose `item_label` is a Wikidata "music of \<place\>" regional-overview article (e.g. "music of Kenya") rather than an actual genre — it also reads a curated `manual_regional_overview_additions.csv` as a backstop for real overview items entirely absent from Bronze (not even as a `parent_label`). `4_regional_classification` cascades the regional-overview seed set down through parent edges to flag every nationally/ethnically-specific genre (e.g. "fado", "morna") as regional, as opposed to canonical genres like "rock music" — it also reads a curated `manual_regional_overrides.csv` (`regional_reason = "manual_override"`) as a backstop for the rare genre none of the automated seed/`indigenous_to`/`country_of_origin` sources catch, a curated `manual_canonical_parent_additions.csv` (columns `item_id,item_label,reason`) for synthetic `LOCAL:`-prefixed canonical grouping nodes with no real Wikidata QID (e.g. `LOCAL:reggae-dub`, "Reggae/Dub"), and a curated `manual_main_parent.csv` (applied as a synthetic edge tagged `manual_main_parent`) letting a data expert pin an item's main parent ahead of step 5 — its optional `exclude_other_parents` column additionally strips an item's other candidate parent edges when needed to override a genuine conflicting edge into the regional seed set. `5_main_parent_selection` picks exactly one main parent per item — the `manual_main_parent.csv` override wins if present, else a provisional lowest-QID heuristic — producing `5_main_parent_selection.parquet`; every other candidate parent edge is kept, not dropped, in a sibling `5_secondary_parents.parquet`. `6_canonical_parents` flags whether each row's chosen main parent is itself a real genre. `7_canonical_hierarchy` is the first step that prunes rather than flags: it collapses the edge list to one row per non-regional genre item, producing `7_canonical_hierarchy.parquet` (canonical, excludes regional items) with an `is_umbrella` flag from the curated `manual_umbrella_genres.csv` (a genre kept in the tree but never assigned songs directly, e.g. techno; an unknown, regional or leaf id raises). `8_regional_hierarchy` mirrors that pruning restricted to regional items, producing `8_regional_hierarchy.parquet`. `9_canonical_roots` extracts `7_canonical_hierarchy`'s root items (no parent) into their own `9_canonical_roots.parquet`, for manual exploration of the "too many roots" open question below — it also reads a curated `manual_accepted_canonical_roots.csv` (whose items `4_regional_classification` pins as parentless roots, so Wikidata re-parenting or `indigenous_to` can't move them; an accepted id that's absent or curated regional raises) and flags (`is_accepted = false`, logged as a WARNING) any root not already in it, rather than failing the run; Gold carries the flag into the canonical tree export as `isUnacceptedRoot: true` so grow-the-music-tree-api queues it for admin review. After them, two artist image steps: `10_commons_image_metadata` caches each Bronze `wikidata_artist_images` file's thumbnail, author and license from the Commons API (30-day TTL, at most `COMMONS_METADATA_MAX_BATCHES_PER_RUN` requests per run), and `11_artist_images` keeps one freely licensed, attributable image per MusicBrainz artist for Gold. See `DESIGN.md` for the rationale and rules behind each step (e.g. the regional cascade's seed set, the main-parent-selection heuristic — several explicitly marked provisional/exploration-phase there) and `SCHEMA.md#3-silver` for the full column definitions and profiling detail. `7_canonical_hierarchy` (canonical) currently surfaces a high number of root items; whether that reflects the source data or an upstream pruning artifact is an open exploration — see `notebooks/explore_genre_tree.ipynb`.

**Curation input:** every `manual_*.csv` this pipeline reads comes from `CURATION_BRONZE_DIR` — the `curation` pipeline's Bronze output, pulled from `grow-the-music-tree-api` (the source of truth, edited via its `curation/<list>/entries/` endpoints or the grow admin UI). Run `uv run --package curation python -m curation.ingest` first. Bronze also reads `manual_entity_additions.csv` for the cultural entities (kind `curated`) and `manual_tradition_additions.csv` for the music-tradition candidates.

**Target shape (design intent, not yet reached):** the canonical tree (`7_canonical_hierarchy`) should collapse down to a handful of root genre families — rock, blues, jazz, funk/disco, electronic, hip-hop, reggae/dub, classical music, etc. — not the hundreds of roots it currently produces. Getting there is expected to be mostly a linking/cleaning problem (correcting mis-selected main parents, e.g. the lowest-QID fallback in `5_main_parent_selection`), not a new extraction or classification mechanism. The regional tree (`8_regional_hierarchy`) follows different logic entirely: one root per cultural/geographic region (e.g. "music of Cape Verde"), with each region's own genres nested underneath — it is not expected to collapse to a small root count the way the canonical tree is.
