## Changelog Best Practices

- Changelogs are for humans, not machines.
- Group changes under: Added, Changed, Improved, Deprecated, Removed, Fixed, Documentation, Performance.
- **"Test" is not a standalone category** — mention tests within the related feature or fix entry.

## [Unreleased]

### Added

- `gold`: `genre_tree_builder.build_genre_tree` now raises if the exported tree contains duplicate node names — mirrors `grow-the-music-tree-api`'s own `tree_value_duplicate` import constraint, failing Gold locally instead of shipping a tree the import will reject.
- `gold`: new on-demand `playground_fixture_export.py` module, flattening `export_canonical_genre_tree`'s nested output into the flat `GenreTreeNode[]` shape the `genre-tree-view` repo's playground fixture consumes, with each node's `itemCount` rolled up from `genre_match`'s resolved song matches (a node's count includes its descendants') — run via `python -m gold.playground_fixture_export <canonical_tree.json> <genre_match.parquet> <output.json>`, not part of `__main__.py`.

### Changed

- `wikidata`: added synthetic `LOCAL:malay-world` "music of the Malay world" regional overview (nested under music of Asia) and routed `Q12501487` (Malay orchestra) to it — it has no `P279` parent and a multi-country `P495`, and its appearance as an unaccepted canonical root failed the 2026-09-21 daily run at `9_canonical_roots`.
- `musicbrainz`: renamed the Silver `song_example` step to `songs` (`3_song_example.parquet` → `3_songs.parquet`, `scripts/export_song_example_json.py` → `scripts/export_songs_json.py`) and removed the `RECORDINGS_PER_GENRE` cap — this dataset is production data consumed by `gold`, not a demo fixture.

- `wikidata`: `item_display_label`/`parent_display_label` now default to a sentence-cased form of `item_label`/`parent_label` (first character capitalized, plus word-level demonym/nationality-adjective capitalization from a new `manual_capitalized_words.csv`) instead of the raw, inconsistently-cased Wikidata label — genre names shown by `gold` and `grow-the-music-tree-api` are now sentence-cased end-to-end. `item_label`/`parent_label` themselves are untouched, still used everywhere as exact-match keys.

### Fixed

- `wikidata`: added the missing `manual_label_overrides.csv` row renaming "pop music" to "Mainstream Pop" — the guard added in 1.2.0 (`export_canonical_genre_tree` requiring that root) shipped with an empty overrides CSV, failing every Gold run.
- `wikidata`: `2_non_genre_pruning` now drops "meme techno" (`Q25408203`), a near-empty Wikidata stub duplicating the real "meme techno" genre item (`Q114238485`), via a new `manual_duplicate_genres.csv` — the two shared a display name in the exported canonical genre tree, which `grow-the-music-tree-api` rejects as a duplicate node name.
- `wikidata`: added `manual_label_overrides.csv` rows disambiguating the remaining 6 duplicate canonical genre names (artcore, darkcore, deathcore, doomcore, electro, wave) by parenthetical genre, e.g. "Deathcore (Techno)" / "Deathcore (Metal)" — each pair is a genuine Wikidata homonym (or, for electro, a same-parent scope overlap), not a duplicate/error, so renaming rather than dropping resolves the `tree_value_duplicate` import constraint.
- `gold`: `__main__` no longer calls `export_regional_genre_tree` — `8_regional_hierarchy.parquet` has 12 duplicate node names (cross-region/era homonyms like "bolero" under both Latin America and Spain, plus a few likely main-parent-selection bugs) that the duplicate-name guard added above now correctly rejects, crashing the whole daily run. Disabled until those are triaged and disambiguated; `1_regional_genre_tree.json` will not be produced or synced to `grow-the-music-tree-api` in the meantime.
- `wikidata`: renamed the three synthetic `LOCAL:`-prefixed grouping node labels ("Blues/Rock", "Disco/Funk", "Reggae/Dub") to add a `" (grouping)"` suffix, and documented the convention in `DESIGN.md` — the real Wikidata item "blues rock" (Q193355) slugified to the same id as the unrelated synthetic "Blues/Rock" grouping node, tripping Gold's genre-name slug collision guard.
- `gold`: `genre_tree_builder.build_genre_tree`'s duplicate node-name guard now compares case-insensitively — a title-cased synthetic grouping node and a real Wikidata item's lowercase label (e.g. "Pop reggae" vs "pop reggae") previously coexisted in the exported tree undetected, since the guard compared names with case-sensitive equality.
- `musicbrainz`: `3_songs`'s YouTube video id extraction now anchors to exactly 11 characters instead of `{6,}` — a handful of real MusicBrainz URLs produced ids either short (truncated) or long (a stray trailing character swallowed into the match), which then failed `grow-the-music-tree-api`'s `varchar(11)` column and aborted its entire songs-import transaction. `gold`'s `genre_match` now also drops any row with a malformed `youtube_video_id` (not exactly 11 characters) before genre matching, as a defensive second check — logged as a warning, not raised, so a regression here can't abort the whole export the way the original bug aborted the whole songs import. `song_export`'s `songs.schema.json` still enforces the same `^[A-Za-z0-9_-]{11}$` pattern as a last-resort net.
- `wikidata`: dropped the synthetic `LOCAL:pop-reggae` grouping node in favor of the real Wikidata item "pop reggae" (Q98528253), re-parented under `Reggae/Dub (grouping)` with "ragga pop" moved to it as a child — the synthetic node's title-cased "Pop reggae" label had silently coexisted with the real item's lowercase "pop reggae" in the exported tree, evading Gold's duplicate-name guard on casing alone.
- `wikidata`: added `manual_label_overrides.csv` rows disambiguating 13 more duplicate node-name groups surfaced by re-enabling the regional tree export (banda music, corrido, Dominican hip hop, mass song, batuque, bolero, bomba, chanson, cumbia, daina, forró, murga, tirana), each a genuine cross-region/era Wikidata homonym, by parenthetical region/scope, e.g. "Bolero (Cuba)" / "Bolero (Spain)".
- `wikidata`: removed the synthetic `LOCAL:nordic-music` regional-overview node — it duplicated the display name of the real, already-linked Wikidata item "music of the Nordic countries" (Q26302245), which serves the same overview role elsewhere in the tree. "Nordic tone" (previously nested under the synthetic node) is now nested directly under Q26302245 instead.
- `gold`: re-enabled `export_regional_genre_tree` in `__main__` now that all duplicate node names in `8_regional_hierarchy.parquet` are resolved — `1_regional_genre_tree.json` is produced and synced to `grow-the-music-tree-api` again.

## [1.0.0] - 2026-09-10

### Added

- New `pipelines/gold` workspace member — the repo's first cross-pipeline consumer, reading both `wikidata`'s and `musicbrainz`'s Silver output. Exports a real canonical genre tree (`1_canonical_genre_tree.json`) from wikidata's `7_canonical_hierarchy.parquet`, replacing the hand-authored JSON previously maintained in `grow-the-music-tree-api`. Reconciles musicbrainz's raw genre-tag names (`3_song_example.parquet`) against wikidata's canonical genre names via a match cascade (exact → `" music"`-suffix stripping → manual alias CSV → manual accepted-non-genre CSV), replacing the naive silent-skip case-insensitive match previously done consumer-side; unmatched names are a soft warning plus a durable `1_genre_match_unresolved.csv` triage report (title/artist/youtube_video_id per unmatched song), not a pipeline-blocking error. Exports `2_songs.json`, the reconciled song list ready for API import. Both JSON exports are validated against a JSON Schema before being written. Runs automatically as part of `gold`'s daily `__main__.py` — no manual/on-demand scripts. See `pipelines/gold/README.md`, `SCHEMA.md`, `DESIGN.md`.
- `wikidata` Silver: `2_non_genre_pruning` now also reads a new git-tracked, hand-curated `manual_umbrella_canonical_genres.csv` (columns `item_id,item_label,reason`), a fourth manual drop-list alongside `manual_theme_genres.csv`/`manual_technique_genres.csv`/`manual_out_of_scope_genres.csv` — for genuine music genres, correctly classified, but too broad to serve as a useful canonical grouping node (e.g. "alternative music", spanning countless pop/rock-deviating subgenres with no single coherent style), as distinct from a misclassification, an off-topic theme, or a technique. Dropping it lets its children (or the item itself, if parentless) surface as their own canonical roots instead of collapsing under one umbrella node. Seeded with "alternative music" (Q1695023) plus five rows migrated from `manual_out_of_scope_genres.csv` that fit this bucket better than "not a genre at all": "popular music" (Q373342), "ethnic music" (Q3570024), "Latin music" (Q18345375), "Western music" (Q2719078), "indigenous music" (Q6024704). See `pipelines/wikidata/DESIGN.md#21-2_non_genre_pruning`.
- `wikidata` Silver: triaged two roots newly orphaned by dropping "alternative music" as an umbrella — "antipop" (Q4034145) added to `manual_main_parent.csv` under "pop music"; "Latin alternative" (Q1089050) added to `manual_regional_overrides.csv` under the `LOCAL:hispanic-world` regional overview, since its other parent ("Latin music") is also excluded as an umbrella. Root count 19 → 18.
- `wikidata` Silver: `9_canonical_roots` now reads a new git-tracked, hand-curated `manual_accepted_canonical_roots.csv` (the set of roots already triaged and confirmed standalone) and raises if a computed root isn't in it, instead of silently writing it out — a diff-based guard-rail so a newly-orphaned item (e.g. from dropping a theme/technique/out-of-scope parent) is caught and triaged rather than reappearing unreviewed. Deliberately diff-based, not a blanket "any orphaned child" check, since dropping a broad umbrella item (e.g. "popular music") legitimately orphans many pre-existing real subgenres (rock, jazz, pop, ska, …) into roots by design. See `pipelines/wikidata/DESIGN.md#281-manual_accepted_canonical_rootscsv-guard-rail`.
- `wikidata` Silver: also curated `9_canonical_roots.parquet` per `.claude/skills/wikidata-canonical-roots/SKILL.md` — mapped/flagged several roots via `manual_main_parent.csv`, `manual_theme_genres.csv`, and `manual_out_of_scope_genres.csv`, bringing the root count from 25 to 21.
- `wikidata` Silver: `4_regional_classification` now also reads a git-tracked, hand-curated `manual_canonical_parent_additions.csv` (columns `item_id,item_label,reason`) as a backstop for synthetic, non-Wikidata canonical grouping nodes — a `LOCAL:`-prefixed parent with no real Wikidata QID (e.g. `LOCAL:reggae-dub`, "Reggae/Dub") that real genre items can nest under via `manual_main_parent.csv` when no single Wikidata item spans the intended grouping. Mirrors the existing `manual_regional_overview_additions.csv` synthetic-id fallback, but for the canonical side. Applied ahead of `manual_main_parent.csv` so the new node is a legal `parent_item_id` target. See `pipelines/wikidata/DESIGN.md#234-manual_main_parentcsv-main-parent-override`.
- `wikidata` Silver: `4_regional_classification` now also reads a new git-tracked, hand-curated `manual_indigenous_to_exclusions.csv` (columns `item_id,item_label,reason`) letting a data expert drop specific `item_id`s from the `P2341`/`indigenous_to` regional-seed source when it's a false positive — e.g. "classical music" carries `indigenous_to = Europe` (a continent, not a specific people/culture), which wrongly pulled it into the regional tree as an orphan root instead of nesting it under "art music" via its real `P279` edge. Unlike `P495`/"country of origin" (already excluded entirely, see `SCHEMA.md#2-bronze`), `P2341` can't be blanket-excluded since it's the only regional signal for some genuinely regional genres (e.g. "Han Chinese music"), so this is a narrow, per-item exclusion instead. See `pipelines/wikidata/DESIGN.md#231-inputs`.

### Changed

- `wikidata` Silver: `5_main_parent_selection`'s automated fallback now prefers a candidate parent that is itself a genre item in the dataset (present as its own `item_id`, not just referenced as a `parent_label`) over one that isn't, before falling back to the lowest QID as a final tiebreak. Fixes 15 items (e.g. "expressionist music", previously mis-parented to the non-genre "Expressionism" art-movement item instead of "modern classical music") that were surfacing as unreviewed orphan roots in `9_canonical_roots.parquet` purely because their real genre parent had a numerically higher QID than a non-genre candidate. Collapsed the canonical root count from hundreds down to 19. See `pipelines/wikidata/DESIGN.md#241-rule-manual-override-else-lowest-qid-heuristic`.
- `wikidata` Silver: `manual_overview_reclassifications.csv` now also reclassifies "religious music" as a regional-overview grouping node (overriding its prior `manual_theme_genres.csv` exclusion), so "Christian music" and "Islamic music" nest under it via `manual_regional_overrides.csv` (with `exclude_other_parents=true`, to drop their conflicting `P279` edges into the regional seed set) instead of remaining ungrouped canonical roots in `manual_accepted_canonical_roots.csv`.
- `wikidata` Silver: `manual_main_parent.csv` gains an optional `exclude_other_parents` column (blank/`"false"` by default, preserving existing behavior) — when `"true"`, the overridden item's other candidate parent edges are dropped entirely rather than just supplemented, needed when an item has a genuine conflicting edge into the regional seed set (e.g. "reggae" → "music of Jamaica" via `P279`) that would otherwise keep it `is_regional=True` via the cascade regardless of the override, since `is_regional` is computed from any of an item's parent edges, not just its eventual main parent. Used to regroup "reggae" and "dub music" as canonical children of the new synthetic "Reggae/Dub" root above, instead of reggae resolving `is_regional`. Note: 18 items previously nested under reggae in the regional hierarchy (e.g. "roots reggae", "dub reggae", "lovers rock") lose their inherited regional status as a result and now appear as reggae's canonical children instead. See `pipelines/wikidata/DESIGN.md#234-manual_main_parentcsv-main-parent-override`.
- `wikidata` Silver: moved main-parent selection out of `5_canonical_parents`/`6_canonical_hierarchy`/`7_regional_hierarchy` and into its own new step, `5_main_parent_selection` (module `main_parent_selection.py`), inserted immediately after the regional cascade (`4_regional_classification`). It picks exactly one main parent per item — the `manual_main_parent.csv` override wins if present, else the provisional lowest-QID heuristic — writing `5_main_parent_selection.parquet`; every other candidate parent edge is kept, not dropped, in a sibling `5_secondary_parents.parquet`. `6_canonical_hierarchy`/`7_regional_hierarchy` no longer need to collapse multiple parents themselves, since `5_main_parent_selection` already guarantees one row per item. Every downstream step shifted up by one position: `5_canonical_parents` → `6_canonical_parents`, `6_canonical_hierarchy` → `7_canonical_hierarchy`, `7_regional_hierarchy` → `8_regional_hierarchy`, `8_canonical_roots` → `9_canonical_roots`. Silver is now a nine-step sequence. See `pipelines/wikidata/DESIGN.md#24-5_main_parent_selection`.
- `wikidata` Silver: renamed `manual_canonical_parents.csv` to `manual_main_parent.csv` and removed its root-only restriction, so a data expert can now pin any item's main parent, not just root items. It's applied as a synthetic edge (tagged `manual_main_parent`) in `4_regional_classification`, ahead of `5_main_parent_selection`, rather than as a post-hoc override in the old `5_canonical_parents`. See `pipelines/wikidata/DESIGN.md#234-manual_main_parentcsv-main-parent-override`.
- `wikidata` Silver: renamed `4_genre_parents`'s `parent_is_genre` column to `parent_is_canonical` — it's only ever consulted by `5_hierarchy`'s canonical pruning (`_prune_canonical`), never by regional pruning, so the old name overstated its scope. See `pipelines/wikidata/DESIGN.md#242-rule-what-counts-as-a-canonical-parent`.
- `wikidata` Silver: renamed the `4_genre_parents` step itself (module, function, and `4_genre_parents.parquet` output file) to `4_canonical_parents`, for consistency with the `parent_is_canonical` rename above.
- `wikidata` Silver: renamed the canonical output of the `5_hierarchy` step from `5_hierarchy.parquet` to `5_canonical_hierarchy.parquet` (and internal path variables/refs to match), for symmetry with the already-explicit `5_regional_hierarchy.parquet`.
- `wikidata` Silver: moved the `manual_theme_genres.csv`/`manual_technique_genres.csv`/`manual_out_of_scope_genres.csv` item drop from `5_canonical_hierarchy` (step 5) to `3_regional_classification` (step 3), so it now runs before the regional cascade rather than after. Hardening only — on current data no dropped item sits upstream of a real genre in the cascade, so this is a no-op today; it guards against a future Wikidata item that would otherwise hand its `is_regional` status down to a real genre beneath it before being pruned. See `pipelines/wikidata/DESIGN.md#23-manual-csv-backstops-for-non-genre-pruning`.
- `wikidata` Silver: split that manual CSV backstop drop out of `3_regional_classification` into its own step, `3_non_genre_pruning`, since dropping theme/technique/out-of-scope items isn't about region at all. Every downstream step and output file shifted up by one position: `3_regional_classification` → `4_regional_classification`, `4_canonical_parents` → `5_canonical_parents`, `5_canonical_hierarchy`/`5_regional_hierarchy` → `6_canonical_hierarchy`/`6_regional_hierarchy`, `6_canonical_roots` → `7_canonical_roots`. Silver is now a seven-step sequence. See `pipelines/wikidata/DESIGN.md#22-3_non_genre_pruning`.
- `wikidata` Silver: swapped the order of `2_regional_overview_classification` and `3_non_genre_pruning` so non-genre pruning now runs first — `2_non_genre_pruning` → `3_regional_overview_classification`. This follows standard "prune ASAP" ETL practice: dropping non-genre rows before regional classification means every step downstream (including `3_regional_overview_classification` itself) works over a smaller, cleaner tree. Steps `4_regional_classification` through `7_canonical_roots` keep their existing numbers/filenames — only their upstream input path changed. See `pipelines/wikidata/DESIGN.md#21-2_non_genre_pruning` and `#22-3_regional_overview_classification`.
- `wikidata` Silver: split the combined `6_canonical_hierarchy` step (which wrote both `6_canonical_hierarchy.parquet` and `6_regional_hierarchy.parquet`) into two independent steps, per the "one asset = one output" convention: `6_canonical_hierarchy` (module `canonical_hierarchy.py`, function `prune_canonical_hierarchy()`) writes only `6_canonical_hierarchy.parquet`; the new `7_regional_hierarchy` step (module `regional_hierarchy.py`, function `prune_regional_hierarchy()`) writes `7_regional_hierarchy.parquet`. Shared collapse/orphan-promotion logic moved to a new `hierarchy_utils.py`. `7_canonical_roots` renumbered to `8_canonical_roots`. Silver is now an eight-step sequence. See `pipelines/wikidata/DESIGN.md#25-6_canonical_hierarchy` and `#26-7_regional_hierarchy`.

### Added

- `wikidata` Silver: `2_regional_overview_classification` now reads a new git-tracked, hand-curated `manual_overview_reclassifications.csv` to flag `is_regional_overview = True` (`classification_reason = "manual_overview_reclassification"`) on items that already exist in the genre tree but function as a non-genre regional overview node despite not carrying the `"music of "` label prefix — e.g. "European folk music" (Q98528192), a continent-wide folk-music umbrella. `3_regional_classification`'s seed set now also includes items with this reason, so regional status still cascades correctly to reclassified items' children. See `pipelines/wikidata/DESIGN.md#215-manual-reclassification-of-existing-items-as-overview`.

- `wikidata` Silver: `6_canonical_roots` now also treats an item as a root when its `parent_id` points at a "phantom" parent — a label (e.g. "popular music") that never has its own row in `5_hierarchy.parquet`, so it can never itself be resolved down to a real ancestor. This was silently dropping the root count to 0 after the previous curation pass linked every remaining rootless item to *some* parent, many of which chained up to such phantoms. `.claude/skills/wikidata-canonical-roots/SKILL.md` documents the new triage case so a major genre family sitting under a phantom umbrella term (e.g. jazz/rock/hip-hop under "popular music") is recognized as a genuine standalone root instead of mis-triaged into `manual_canonical_parents.csv`.

Flag-only, no rows dropped. **Exploration-phase finding, expected to evolve**: on a real run, ~53% of all items (3,377 of 6,338) end up flagged `is_regional` (299 seed, 1,392 direct, 1,686 inherited) — far more than initially expected — because several of the `regional_overview` seeds are continent-level ("music of Asia", "music of Europe", ...) with very large fan-out. Kept as-is for now rather than narrowing the seed set, since the design is still exploratory; see `SCHEMA.md#2_regional_classification`'s "Exploration phase" callout. Also flags, as a follow-up investigation (not a code gap): "variété française" doesn't appear anywhere in the current Bronze extraction at all, so it can't be classified either way.
- `wikidata` Silver layer, `3_genre_parents` (renumbered from `2_genre_parents`): adds a `parent_is_genre` column flagging whether each edge's `parent_id` is itself flagged `is_regional_overview = False` by `1_regional_overview_classification` (not just present in Bronze's raw `P31` extension) — lets the hierarchy step filter to genre-only edges without redoing classification. Flag-only, no rows dropped. `wikidata.silver.profile` now also prints its breakdown. See `SCHEMA.md#silver`, which now also has a `3_genre_parents` data profile (6,248 `true` / 2,988 `false` / 488 `null` root rows, as of this writing).
- `pipelines/wikidata/notebooks/explore_genre_tree.ipynb`: new "Silver exploration" section reading `3_genre_parents.parquet` — `is_regional_overview`/`classification_reason` breakdown, sample tagged items, and `parent_is_genre` breakdown with sample non-genre-parent edges.
- `pipelines/wikidata/notebooks/explore_genre_tree.ipynb`: new cell listing `4_hierarchy`'s canonical root items (`parent_id` null, non-regional), to start investigating whether their high count is a real property of the source data or an artifact of the upstream pruning/collapse rules. See `SCHEMA.md#4_hierarchy`'s "Under exploration" callout.
- `wikidata` Silver layer, `4_hierarchy` (renumbered from `3_hierarchy`): the first Silver step that drops rows rather than flagging. Prunes `3_genre_parents.parquet` to genre-only edges, then collapses each remaining multi-parent item down to a single row by keeping the parent with the lowest numeric QID — **a provisional, tâtonnement heuristic, not a settled design decision**: ~43% of genre items (2,727 of ~6,337) have more than one surviving genre parent, and only 1 item in the whole genre extension has a Wikidata "preferred rank" `P279` statement, so no reliable disambiguation signal currently exists; expect this rule to be revisited once a real product/curation decision is made. Now produces **two** outputs instead of one — `4_hierarchy.parquet` (canonical, excluding every `is_regional = true` item) and `4_regional_hierarchy.parquet` (regional, containing only `is_regional = true` items, including the `regional_overview` seeds themselves as real nodes with real parent chains rather than synthetic roots — e.g. morna keeps its real parent edge into "music of Cape Verde" instead of being promoted). `item_id` is unique in both outputs, unlike every prior Bronze/Silver artifact. `wikidata.silver.profile`'s `profile_hierarchy` now reports both outputs' row counts plus the count of genre items surviving in *neither* output (299, as of this writing). See `SCHEMA.md#4_hierarchy`.
- `wikidata_client.py`/`explore_genre_tree.ipynb`: clarified the `P31`/`P279`/`P361` usage comments and query docstring — `P31` finds the genre set, `P279`/`P361` build hierarchy edges, never the other way around — and fixed a stale `P279` example ("heavy metal" is a subclass of "metal music", not "rock music" directly). No behavior change.

### Fixed

- `musicbrainz` Bronze ingestion: pass `infer_schema_length=BATCH_SIZE` to `pl.read_database` — Polars was inferring each batch's column types from only its first 100 rows, so a batch with early-row `NULL`s in a `datetime` column followed by a real value later in the same batch could raise `ComputeError: could not append value ... make sure that all rows have the same schema`.
